## Confirmed findings

### 1. P2 — Expired login-backoff entries accumulate indefinitely

Location: [authLimiter.ts:113](E:/Programming/Enjoyer/api/src/lib/authLimiter.ts:113), with insertion at [line 144](E:/Programming/Enjoyer/api/src/lib/authLimiter.ts:144).

When Redis is not configured, each distinct email that receives a failed login creates an entry in `memoryBackoff`. The 15-minute expiry is checked only when that same email is requested again. There is no periodic sweep or size limit, so abandoned keys remain for the lifetime of the process.

Reproduction: an isolated harness executed the source's actual backoff logic with Redis disabled and 1,000 distinct synthetic failed-login emails. After advancing the clock by 24 hours and processing an unrelated login, all 1,000 expired entries remained. The harness stubbed external dependencies and inspected the private map; it did not send login traffic or touch real accounts.

Impact: memory use grows with distinct failed-login addresses over uptime. Existing request limits reduce the growth rate but do not bound retained memory. Sustained or distributed traffic can worsen this.

Recommended fix: use a bounded cache with expiry eviction, or periodically sweep expired entries and enforce a maximum size. Add a fake-clock regression test that verifies entries disappear without revisiting their keys.

### 2. P2 — Concurrent refreshes after a network change falsely trigger theft detection

Location: [sessions.ts:182](E:/Programming/Enjoyer/api/src/lib/sessions.ts:182), with the first-use update at [line 208](E:/Programming/Enjoyer/api/src/lib/sessions.ts:208).

The grace-window check compares requests with the fingerprint recorded when the token was issued. A first refresh from a new IP is deliberately accepted, but it updates only `usedAt` on the old token. A second refresh using that same token from the same new IP, within the 10-second grace window, still differs from the old stored IP. The code classifies it as theft and revokes the entire family, including the token just issued.

Trigger: two browser tabs refresh after switching from one network to another, or a retry follows that first refresh before the updated cookie is available.

Reproduction: invoked the actual `rotateSession` implementation using a mocked database, with a token issued to synthetic IP A. The first call from IP B succeeded; the immediate second call from IP B returned `reason: "reuse", cause: "grace"` and revoked the new token. This exercises the serialized request order; it does not prove PostgreSQL concurrency behavior.

Recommended fix: record the fingerprint that first consumed the token and compare grace-window replays against that fingerprint. Preserve rejection of a replay from a different consuming client. Add tests for same-network races, changed-network races, different-client replays and requests outside the grace window.

## Incomplete work and verification gaps

- **Table/QR feature is not ready.** [app.ts:79](E:/Programming/Enjoyer/api/src/app.ts:79) mounts public table resolution, and lines 89–90 mount protected table routes. A read-only query against the configured database confirmed `public.shop_tables` does not exist. [0004_shop_tables.sql](E:/Programming/Enjoyer/api/drizzle/0004_shop_tables.sql) is present locally. Database-reaching table requests will fail until it is applied. This is work interrupted by the audit request, not a newly discovered regression. Table-specific tests, Postman requests and documentation are also absent. No migration was applied during the audit.
- **Concurrency is not tested against PostgreSQL.** The existing suites use scripted database replies. For example, [auth.test.ts:60](E:/Programming/Enjoyer/api/tests/auth.test.ts:60) implements a transaction as a callback without real locking. Add isolated database integration tests for simultaneous Owner changes, reset-token consumption, refresh versus revocation, and option-link replacement. Do not run destructive tests against the seeded shop database.
- **Rate-limit behavior is bypassed in auth tests.** [auth.test.ts:111](E:/Programming/Enjoyer/api/tests/auth.test.ts:111) replaces the rate limiters with pass-through middleware. Add focused tests for expiry, thresholds and Redis outage/recovery behavior.
- **Type checking has a limited file set.** [tsconfig.json](E:/Programming/Enjoyer/api/tsconfig.json) includes application code and menu seed scripts, but excludes the test files and `scripts/seed-owner.ts`. The successful type check therefore does not cover those files.
    
## Dependencies and operational limits

`npm audit --omit=dev --json` reported **zero known production dependency vulnerabilities**. The full audit reported **four moderate entries from one development dependency chain**: `drizzle-kit` → `@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils` → `esbuild`.

The underlying [esbuild advisory](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99) concerns cross-origin access to its development server. The API start script runs Node directly; this review did not establish an exposed vulnerable esbuild server. Track a compatible tooling update. npm's suggested forced fix changes Drizzle Kit to an older major-version line, so it should not be applied blindly. No dependencies were changed during the audit.

Existing documented tradeoffs remain:

- Logout and password changes revoke refresh sessions, while existing access JWTs remain valid until expiry: one minute in production and ten minutes in development/test. Deactivation blocks access immediately through the current-account check; reactivation can make an unexpired old JWT usable again. These semantics are documented in the README.
- Background password emails use in-process retries rather than durable delivery. Process termination can lose queued mail, and graceful shutdown does not drain those sends. Treat a durable outbox or a bounded shutdown drain as operational hardening before deployment.
- Redis and the breached-password lookup deliberately fail open during outages. Real Redis/SMTP/HIBP outage behavior was not exercised in this audit.
